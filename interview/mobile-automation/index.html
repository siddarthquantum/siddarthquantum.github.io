1. Appium 2.x architecture

Appium is an open-source automation server that speaks the W3C WebDriver protocol. A language client (Java, Python, JavaScript, C#) sends HTTP commands to Appium. Appium routes them to a driver, which talks to the OS automation backend: UiAutomator2 on Android, XCUITest on iOS (WebDriverAgent on the device), and optionally Espresso, Flutter, or a mobile browser.

Appium 1.x shipped every driver inside the server. Appium 2.x splits the core from drivers and plugins. You install a slim server, then only the drivers you need. Drivers release on their own cadence, the install is smaller, and plugins (images, execute-driver, inspector helpers) compose without forking Appium.

That split is the usual follow-up. XCUITest can ship an iOS support fix without waiting for a full Appium core release.

npm install -g appium
appium driver install uiautomator2
appium driver install xcuitest
appium plugin install images
appium driver list --installed
appium --port 4723
Driver When to use Trade-off
UiAutomator2 Black-box Android native and hybrid Default choice. No app source. Slower and less animation-aware than Espresso.
Espresso White-box Android with instrumentation Needs a debug APK. Better idle sync. Weaker for third-party / system UI.
XCUITest iOS native, hybrid, Safari Xcode, signing, UDID, WebDriverAgent. Version skew is the main setup failure.

Do not say “Appium automates the app.” Say: client → W3C HTTP → Appium server → driver → UiAutomator2 / WDA → app process. The session id on that path is what every later find/click/screenshot uses.

2. Capabilities and sessions

JSON Wire Protocol desiredCapabilities is legacy. Appium 2 with current clients uses W3C capabilities (alwaysMatch / firstMatch). Standard keys include platformName and browserName. Vendor keys must be prefixed with appium: or they are rejected. Java and Python clients hide the prefix behind option classes. 

UiAutomator2Options opts = new UiAutomator2Options()
    .setPlatformName("Android")
    .setAutomationName("UiAutomator2")
    .setDeviceName("Pixel_7")
    .setUdid("emulator-5554")
    .setApp("/path/to/app.apk")
    .setAppPackage("com.example.app")
    .setAppActivity(".MainActivity")
    .setNoReset(true)
    .setNewCommandTimeout(Duration.ofSeconds(300));

AndroidDriver driver = new AndroidDriver(
    new URI("http://127.0.0.1:4723").toURL(), opts);
  • noReset keeps app data (logged-in flows). fullReset uninstalls / reinstalls.
  • Android also has a fast-reset path that clears data without a full uninstall.
  • autoGrantPermissions on Android vs iOS alert handling (autoAcceptAlerts is blunt).
  • newCommandTimeout kills idle sessions. Too low looks like “random session deleted.”
  • Cloud farms add build name, project, network logs, GPS, and device logs as extra caps.

iOS equivalents: XCUITestOptions, bundleId or app (.ipa / .app), udid, wdaLocalPort, xcodeOrgId / signing, and often updatedWDABundleId.

3. Locator strategies

Rank locators by stability first, then speed. Prove them in Appium Inspector against the current XML tree. Never defend XPath as a default.

Strategy Maps to Use when
Accessibility ID Android content-desc, iOS accessibilityIdentifier Best cross-platform contract. Fast. Survives layout refactors if the product team owns the id.
ID / resource-id com.app:id/login_btn Excellent on Android. On iOS, name/id mapping is less consistent.
-android uiautomator new UiSelector().resourceId(...).text("Pay") Native Android queries. Prefer over deep XPath. Keep chains short.
-ios predicate string type == 'XCUIElementTypeButton' AND name == 'Pay' Preferred iOS locator after accessibility id.
-ios class chain **/XCUIElementTypeCell[`name == "Card"`] Faster than XPath on iOS. Still a tree walk.
Class name android.widget.Button Too coarse unless combined with something unique. Index is fragile.
XPath //android.widget.TextView[@text='Pay'] Last resort. Slow XML walk. Avoid //* and absolute /hierarchy/... paths.
Image / OCR plugins Appium Images plugin Canvas, games, or unlabeled icons. Flaky across density, theme, and locale.

After a WebView context switch, use web locators (CSS first). Native locators do not apply inside WEBVIEW_*. 

driver.findElement(AppiumBy.accessibilityId("login.submit"));
driver.findElement(AppiumBy.androidUIAutomator(
    "new UiSelector().resourceId(\"com.example:id/pay\")"));
driver.findElement(AppiumBy.iOSNsPredicateString(
    "type == 'XCUIElementTypeButton' AND name == 'Pay'"));

4. W3C Actions (TouchAction is dead)

JSONWP TouchAction and MultiTouchAction are deprecated. Interviews expect the W3C Actions API: pointer input sources, a sequence of pointerMove / pointerDown / pause / pointerUp, then perform(). Derive coordinates from the viewport or an element rect—not magic pixels from one phone. 

PointerInput finger = new PointerInput(PointerInput.Kind.TOUCH, "finger");
Sequence swipe = new Sequence(finger, 1);
Dimension size = driver.manage().window().getSize();
int startX = size.width / 2;
int startY = (int) (size.height * 0.80);
int endY = (int) (size.height * 0.20);

swipe.addAction(finger.createPointerMove(
    Duration.ZERO, PointerInput.Origin.viewport(), startX, startY));
swipe.addAction(finger.createPointerDown(PointerInput.MouseButton.LEFT.asArg()));
swipe.addAction(finger.createPointerMove(
    Duration.ofMillis(600), PointerInput.Origin.viewport(), startX, endY));
swipe.addAction(finger.createPointerUp(PointerInput.MouseButton.LEFT.asArg()));
driver.perform(List.of(swipe));
  • Tap: move to center → down → short pause → up.
  • Long press: same, with a 1–2s pause before up (context menus, drag handles).
  • Swipe / scroll: duration matters. Too fast = no scroll; too slow = a drag.
  • Pinch / zoom: two pointer sources in the same perform() list.
  • Also mention driver helpers: Android mobile: swipeGesture / mobile: scrollGesture; iOS mobile: swipe / mobile: scroll.
driver.executeScript("mobile: swipeGesture", Map.of(
    "left", 100, "top", 400, "width", 600, "height", 800,
    "direction", "up",
    "percent", 0.75
));

5. Hybrid apps, waits, and flake control

Hybrid checkout bugs are a favorite panel topic: Inspector shows the button, the test gets NoSuchElementException, and the log never left NATIVE_APP.

  • Poll driver.getContextHandles() until the expected WEBVIEW_* appears, then context().
  • Chrome / Chromedriver must match the device WebView. Appium 2 drivers can autodiscover if configured.
  • iOS WebViews need inspectable web content; otherwise the WEBVIEW handle never appears.
  • Prefer explicit waits. Do not mix a large implicit wait with WebDriverWait.
  • Flake is usually animation, keyboard covering the CTA, system dialogs, or a stale hierarchy—not “Appium is random.”
new WebDriverWait(driver, Duration.ofSeconds(20)).until(d ->
    d.getContextHandles().stream().anyMatch(c -> c.contains("WEBVIEW")));
String webview = driver.getContextHandles().stream()
    .filter(c -> c.contains("WEBVIEW"))
    .findFirst()
    .orElseThrow();
driver.context(webview);

6. Devices, parallel execution, and CI

  • Emulators / simulators: cheap PR checks. Weak for OEM skins, real GPS, biometrics, push, and performance.
  • Real devices / farms: BrowserStack, Sauce Labs, LambdaTest, AWS Device Farm for nightly matrix runs.
  • Parallel: one session per UDID. Unique systemPort (Android) and wdaLocalPort / mjpegServerPort (iOS). Never share one driver across threads.
  • CI: build the APK/IPA in the same pipeline, inject caps from secrets, shard by device, attach Appium server log + screenshot + video on failure.
  • Deep links: am start -a android.intent.action.VIEW -d "myapp://checkout" (or iOS URL schemes) skip long navigations and cut flake.

7. Top interview questions

Q1. How does Appium talk to a device? Client library → W3C WebDriver HTTP → Appium server → platform driver (UiAutomator2 / XCUITest) → OS engine → app. The session id binds later commands to that device.
Q2. What changed in Appium 2.x? Drivers and plugins are separate packages. Protocol is W3C-first. Vendor caps need the appium: prefix. You must appium driver install instead of assuming everything is bundled.
Q3. Desired capabilities vs W3C options? JSONWP used a flat desiredCapabilities map. W3C uses alwaysMatch/firstMatch. Java clients wrap this in UiAutomator2Options / XCUITestOptions. Unprefixed vendor keys fail session creation.
Q4. UiAutomator2 vs Espresso vs XCUITest? UIA2: black-box Android, no source. Espresso: in-process Android, needs instrumentation, better sync. XCUITest: iOS only, WDA on device, signing and UDID pain.
Q5. Which locator do you choose first? Accessibility ID → resource-id / iOS predicate → class chain or UiSelector → relative XPath. Justify from Inspector XML, not habit.
Q6. Why is XPath disliked on mobile? Page source is a large XML dump. XPath walks the tree, breaks when wrappers change, and is slower than native selectors—especially //*.
Q7. How do you automate a swipe without TouchAction? W3C PointerInput sequence with viewport percentages, or driver.executeScript("mobile: swipeGesture", args). Mention duration. Do not hardcode 500,1500.
Q8. How do you wait for a WebView? Poll contexts until the WEBVIEW handle exists, then switch. If it never appears: wrong package, Android web debugging disabled, or iOS webview not inspectable.
Q9. Real device vs emulator? Emulators for fast CI. Real devices / farms for OEM WebView, permissions, biometrics, and performance. Strong answer: both, with different jobs.
Q10. noReset vs fullReset? noReset keeps state (stay logged in). fullReset reinstalls. Wrong choice is a common “works on my machine” bug after a failed logout cleanup.
Q11. How do you run tests in parallel? Unique UDID, ports, and driver instances. TestNG/JUnit or pytest-xdist plus a farm. One Appium server can host multiple sessions if ports do not collide.
Q12. How do you handle permission dialogs? Android: autoGrantPermissions or adb shell pm grant. iOS: autoAcceptAlerts or explicit SpringBoard alert locators. Do not sleep and hope.
Q13. Inspector shows the button; the test cannot find it. Why? Wrong context, stale hierarchy after animation, toast overlay, or a locator that matches a different node. Dump page source, screenshot, and context list at failure.
Q14. What is WebDriverAgent? The XCUITest driver installs WDA on the iOS device. Appium proxies to it. Signing, iOS version mismatch, and a stale WDA are the top iOS setup failures.
Q15. How is Appium different from Detox or Maestro? Appium: black-box, any stack, WebDriver, slower. Detox: gray-box React Native with idle sync. Maestro: YAML flows, fast to author, weaker as a full language framework.
Q16. How do you assert a toast? Toasts are transient. Use a short explicit wait on text, UiAutomator toast capture, or logcat. Do not Thread.sleep(5000).
Q17. Biometrics, OTP, SMS? Farms expose biometric inject helpers. OTP: test hooks, mock inbox, or backend seed. Avoid scraping production SMS if a hook exists.
Q18. What belongs in a CI failure artifact? Appium server log, device log, screenshot, optional video, capability dump, and the page source. Without those, flake is undebuggable.
Q19. How do you stop a long navigation from making tests flaky? Deep links, seeded test accounts, noReset where safe, and APIs to put the app in a known state before the UI assertion.
Q20. Walk through a flaky checkout. Reproduce on one UDID → Inspector vs failure screenshot → context list → locator uniqueness → wait for clickable → disable animations → pin driver versions → add a targeted wait, not a global sleep.
Q21. What is newCommandTimeout? Seconds Appium waits between commands before killing the session. Long explicit waits plus a low timeout look like infrastructure flake.
Q22. Can one script cover Android and iOS? Shared flow and accessibility ids, yes. Separate drivers, caps, and some locators. Abstract the driver behind a page object; do not pretend every locator is identical.

8. How to answer in the room

  • Name versions: Appium 2.x, UiAutomator2 / XCUITest, and the client (Java client 9, Python Appium 4, or WebdriverIO).
  • Bring one incident: WebView context, WDA signing, Chromedriver mismatch, or a parallel port clash.
  • If mobile experience is thin, say so. Walk architecture, locator ranking, and W3C Actions honestly. Curiosity beats invented farm war stories.
  • When they ask you to write code, prefer W3C options + AppiumBy + an explicit wait + a pointer sequence.
